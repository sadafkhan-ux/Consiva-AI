## Later the same day: "different results each time" and dashboard score not equal to the PDF score
Investigation (read-only, stored data). The dashboard and the PDF page build the score with the same function (`reportModelFromState` then `buildTenChecks`) from the same loader (`useConsentScan.open`), so they can only differ when the data they hold differs at the moment they read it.
- **Root cause of dashboard vs PDF:** the dashboard stopped waiting when the analysis findings were ready (`analysisStagesAreDone` accepts `findings_generated`), and loaded the policy result once at that moment. The policy reading runs beside the analysis and can still be running (the server only guarantees it is done by `audit_saved`, after a human review). A scan whose policy reading finished seconds later was scored on the dashboard with checks 2 to 7 left out (66.7) and in the PDF, built later from the finished result, with all of them (94.4). The weighted DPDP score, which reads the policy result, was stale for the same reason. Fix: `settlePolicyAnalysis` in `useConsentScan.ts` polls until the `policy_analysis` stage is completed or failed (bounded at 300 s), then loads the policy result and the weighted score again; the phase stays "analyzing" meanwhile, so the hero shows "Assessing" and no number. A failed policy reading no longer makes the whole run "failed" (it is fail-soft on the server): `policy_analysis` is now an analysis stage, so the run ends "degraded" with those checks Not Assessed.
- **Run-to-run differences, measured on stored scans of the same sites** (115 scans of swaransoft.com, 3 each of cookieyes.com and bbc.com, 4 of wipro.com): the pages chosen are identical every time; the score-relevant consent measurements are stable for swaransoft, wipro, cookieyes and icicibank (before consent, after Accept and after Reject counts identical); counts that do not feed the score drift (tracker totals 36 to 60 over all of swaransoft's history but 50 or 51 recently, forms 3 or 7, a cookie total off by one on wipro). bbc.com, which loads ads, varies a lot in tracker counts (39 to 52 before consent) without changing any check's outcome. One of five recent swaransoft scans had no policy analysis at all (`not_run`), which is what moves a score. So the drift that changes a score comes from the policy reading, as found earlier today (sharing and retention rescue, cut-policy handling).
- **New this round:** the reuse key of a policy analysis (`reuse_prompt`) is built from normalised document text, so two scans of an unchanged policy rendered with a different line break, non-breaking space or quote style ask the same question and reuse the stored answer instead of asking the model again. A changed word, page or requirement still changes it.
Tests: 4 new hook tests (`openScan.test.tsx`: the page stays in "analyzing" until the policy reading is done and then holds the finished result; the weighted score is loaded again after it; a scan with no policy stage does not wait; a failed reading is never "failed"); 2 new backend tests (reuse key). Frontend 1,162 passed, type check clean.
Not verified: a live scan on the dashboard. Not changed: the measurement variance in tracker and form counts on busy sites (they do not move a check).
